# دليل نشر وتشغيل بُعد

هذا الدليل لفريق التشغيل. يفترض خادم Linux عليه Docker، ويعمل على أي مزوّد استضافة.

## ١. ما الذي يعمل على الخادم

| الخدمة | الوظيفة |
|---|---|
| `caddy` | المدخل الوحيد من الإنترنت (المنفذان 80 و443)، ويصدر شهادة HTTPS تلقائيًا لنطاقك |
| `app` | التطبيق: لوحة الفريق، بوابة العميل، والـ API |
| `worker` | الرسائل والتذكيرات والتجديدات ومتابعة الشركات وقراءة بريد العروض. **نسخة واحدة فقط** |
| `db` | PostgreSQL. غير مكشوفة للإنترنت |
| `backup` | نسخة احتياطية يومية لقاعدة البيانات والمستندات |
| `migrate` | تُشغَّل مرة واحدة مع كل نشر لتحديث قاعدة البيانات |

الملفات كلها في مجلد `deploy/`.

## ٢. التجهيز لأول مرة

**متطلبات الخادم:**
- 2 vCPU وذاكرة 4GB وقرص 40GB على الأقل.
- Docker مع إضافة compose.
- نطاق (مثل `app.bud.sa`) يشير سجل A فيه إلى عنوان الخادم.

**الخطوات:**

1. أنشئ مجلدًا على الخادم مثل `/opt/bud`، وانسخ إليه:
   - محتويات `deploy/`.
   - الملف `.env.example` باسم `.env`.
2. عدّل `.env`:
   - `DOMAIN`.
   - `POSTGRES_PASSWORD`: كلمة مرور طويلة عشوائية.
   - `DATABASE_URL`: بنفس كلمة المرور، والمضيف `db`.
   - `BUD_IMAGE=ghcr.io/<حساب-github>/bud`.
   - بيانات البريد SMTP.
   - تأكد من `ENVIRONMENT=production`.
3. سجّل الخادم في سجل الصور:
   ```
   echo <token-بصلاحية-read:packages> | docker login ghcr.io -u <حساب-github> --password-stdin
   ```
4. أول نشر:
   ```
   cd /opt/bud && ./deploy.sh latest
   ```
5. أنشئ أول مدير:
   ```
   docker compose -f docker-compose.prod.yml --env-file .env exec -e BUD_ADMIN_PASSWORD='...' app \
     python -m app.cli create-manager --email you@bud.sa --name "اسمك"
   ```
6. ادخل على `https://<DOMAIN>/dashboard/login.html`، ثم أضف الفريق من «الإعدادات».

**البيئة التجريبية (staging):** نفس الخطوات على خادم آخر، مع `ENVIRONMENT=staging`. تقدر تضيف بيانات تجريبية بالأمر `python -m app.cli seed-demo`، وهو لا يعمل أبدًا في الإنتاج.

## ٣. النشر الآلي (GitHub Actions)

- **`ci.yml`** يعمل مع كل تغيير، ويشمل:
  - التنسيق وفحص الأنواع والاختبارات.
  - تطبيق الترحيلات على PostgreSQL حقيقي ومطابقتها للنماذج وإرجاعها.
  - بناء الصورة.
- **`release.yml`** يعمل مع كل دمج في `main`:
  1. يبني الصورة ويرفعها إلى `ghcr.io` بوسم مثل `20261015-ab12cd34`.
  2. ينشر على **staging** تلقائيًا.
  3. ينشر على **production** بعد موافقة شخص مخوّل.

**الإعداد مرة واحدة في GitHub (Settings ← Environments):**
- أنشئ البيئتين `staging` و`production`، وفعّل **Required reviewers** على `production`.
- أضف لكل بيئة هذه الأسرار:
  - `DEPLOY_HOST`
  - `DEPLOY_USER`
  - `DEPLOY_SSH_KEY`: مفتاح خاص لمستخدم على الخادم في مجموعة docker.
  - `DEPLOY_PATH`: مثل `/opt/bud`.
- الخطّان مضبوطان على فرع `main`. إذا كان الفرع الرئيسي باسم آخر، عدّل `branches` في الملفين.

**ماذا يفعل `deploy.sh` في كل نشر:**
1. يسحب الصورة الجديدة.
2. يأخذ نسخة احتياطية قبل أي تغيير.
3. يشغّل الترحيلات.
4. يعيد تشغيل التطبيق والعامل.
5. ينتظر نجاح `/health/ready`.
6. إذا لم تصبح النسخة سليمة، **يرجع تلقائيًا للنسخة السابقة**.

**ملاحظة عن الترحيلات:** الترحيلات لا تُرجَع تلقائيًا، لأنها مكتوبة بحيث تضيف ولا تحذف. لذلك النسخة السابقة تشتغل على قاعدة أحدث، وفحص الجاهزية يعتبر ذلك سليمًا.

**النشر اليدوي لوسم محدد:**
```
cd /opt/bud && ./deploy.sh 20261015-ab12cd34
```

## ٤. النسخ الاحتياطي والاسترجاع

- **متى:** نسخة يومية في الساعة `BACKUP_HOUR_UTC`، ونسخة إضافية قبل كل نشر.
- **أين:** في وحدة التخزين `backups`، ملفان لكل نسخة:
  - `db-*.dump` لقاعدة البيانات.
  - `uploads-*.tar.gz` لمستندات العملاء.
- **مدة الاحتفاظ:** `BACKUP_RETENTION_DAYS` يومًا.
- **انسخها خارج الخادم.** النسخ على نفس الخادم لا تحميك إذا فُقد الخادم. أضف مهمة cron تنقل ملفات المجلد يوميًا إلى تخزين آخر داخل المملكة.

**نسخة فورية:**
```
docker compose -f docker-compose.prod.yml --env-file .env exec backup sh /usr/local/bin/backup.sh --once
```

**الاسترجاع** (يستبدل كل البيانات الحالية، ويطلب كتابة `RESTORE` للتأكيد):
```
./restore.sh db-20261015-000000.dump uploads-20261015-000000.tar.gz
```

**جرّب الاسترجاع على staging مرة كل شهر.** النسخة التي لم تُجرَّب لا يُعتمد عليها.

## ٥. المراقبة

| ماذا | أين |
|---|---|
| هل التطبيق يعمل؟ | `https://<DOMAIN>/health`، اربطه بخدمة مراقبة توفر (مثل UptimeRobot) |
| هل القاعدة متصلة ومحدّثة؟ | `https://<DOMAIN>/health/ready`، ويرجع 503 إذا في مشكلة |
| الأخطاء | ضع `SENTRY_DSN` في `.env`. بيانات العملاء لا تُرسل للمتتبع |
| السجلات | `docker compose -f docker-compose.prod.yml logs -f app worker`. كل طلب له `X-Request-ID` يظهر في السجل وفي رد الخادم |
| الرسائل الفاشلة وردود الشركات | من لوحة الفريق: «الإعدادات ← الأتمتة والرسائل» و«الاكتتاب ← ردود الشركات» |

## ٦. قبل التشغيل الفعلي مع العملاء

- [ ] **الاستضافة:** الخادم وقاعدة البيانات والنسخ الاحتياطية داخل المملكة، وفق نظام حماية البيانات الشخصية ومتطلبات هيئة التأمين.
- [ ] **مراجعة الامتثال** لما يُؤتمت وكيف يُوثّق.
- [ ] **التحقق بالرمز (OTP):** متابعة الطلب للعملاء تعتمد على وصول رمز التحقق. لا تفعّلها للعملاء قبل تفعيل مزوّد الرسائل.
- [ ] **مزوّد الرسائل:** تفعيله (Unifonic أو واتساب) واعتماد قوالب واتساب من Meta، ثم التحويل إلى «فعلي» من الإعدادات.
- [ ] **بريد العروض:** إعداد SMTP للإرسال وIMAP لاستقبال ردود الشركات.
- [ ] **الذكاء الاصطناعي:** قرار مكتوب قبل تفعيل `AI_QUOTE_EXTRACTION_ENABLED`، لأنه يرسل رسائل الشركات ومرفقاتها إلى Anthropic.
- [ ] **النسخ خارج الخادم** وتجربة استرجاع ناجحة.
- [ ] **مراقبة التوفر** و`SENTRY_DSN` مفعّلان.
- [ ] **الحسابات:** تغيير كلمة مرور المدير الأولى، وأن كل موظف بحسابه ودوره الصحيح.
